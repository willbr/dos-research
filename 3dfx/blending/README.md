# Winchester / candlelight blending

A native C / DOS / Glide blending demo set in a Winchester-inspired nave:
pointed stone vaults and arcades, thirteen stained-glass windows, twelve
candles, colored floor-light patterns and low translucent mist. It is an
interpreted interior for the experiment, not a measured reconstruction of
Winchester Cathedral or reproductions of its historic glass.

Run `run.cmd` or `./run.ps1`. The automatic nave tour starts immediately.
The model has 4,808 vertices and 2,378 opaque triangles, with up to 52
transparent/additive quads collected each frame.

## Controls

| Input | Action |
| --- | --- |
| G | Toggle translucent stained-glass panes. |
| C | Toggle flickering candle flames and additive halos. Opaque stands remain. |
| M | Toggle mist sprites. |
| L | Toggle the patterned additive light patches on the floor. |
| S | Compare back-to-front sorting with deliberately reversed order. |
| F | Switch between the automatic nave tour and manual look/dolly. |
| Space | Pause/resume the tour and effect animation. |
| Left drag / arrows | Smooth look with acceleration and flick inertia; returns to manual mode. |
| Wheel / right drag / + / - | Dolly near the current position, staying inside the central aisle. |
| R / middle click | Reset the manual camera; middle click also pauses. |
| Tab | Stage timings, FPS/frame-time graphs and P95/max frame time. |
| Escape | Exit to DOS. |

Click to capture the mouse; Ctrl+F10 releases it. Pause before comparing
individual effects or sorting order so camera motion and flame flicker do
not obscure the difference. The switches are independent: G does not
implicitly turn off L, for example.

The roughly 80-second tour follows a closed, arc-length-resampled camera
path inside the nave, looking along the aisle and toward the windows. Mode
changes blend position/look direction; manual movement is bounded away
from the piers and end walls.

## Blend pipeline

Opaque masonry, floor, stands and wax are drawn first with depth writes on.
Transparent work keeps depth testing on and disables depth writes. Quads
are sorted by camera-space center depth, including the additive elements,
so a nearer mist card can attenuate a more distant glow.

- Glass and mist use `SRC_ALPHA, ONE_MINUS_SRC_ALPHA`.
- Flame, halo and floor-light contributions use `SRC_ALPHA, ONE`.
- Texture alpha is multiplied by vertex alpha with `grAlphaCombine`.
- Completely transparent texels are rejected; the sprite rectangle remains
  invisible. Sprites fade before crossing the camera's near plane.
- Opaque foreground surfaces can reject glows through the ordinary depth
  test. The additive pass does not paint through stone.

The glass is generated as ARGB4444: colored geometric panes, dark leading,
pointed stone frames and a small rosette. Its separate floor-light cookie
excludes the opaque stone/leading. Those light patterns are hand-placed,
sheared floor quads mapped with the same colored panes. They approximate
colored light visually; they do not trace light through the glass or compute
shadows. Candle lighting likewise uses static warm surface lighting plus
animated additive sprites, rather than a physical illumination model.

Center-depth sorting is a useful control, not a solution for arbitrary
intersecting transparent geometry. S reverses that same order. The separate
flat-quad control below establishes the blend equation without that spatial
approximation. Mist here is alpha-blended geometry, not Glide's fog table.

There are no programmable shaders or modern transparency buffers. Stone
and paving reuse the existing material files from `../textures/assets/`.
Glass, light cookie, flame, soft alpha sprite and font are generated by C
at startup; no new reference photos or bitmap artwork are saved.

## Configuration and performance

The main config uses DOSBox-X's OpenGL Voodoo backend, native Glide with
passthrough off, fixed 100,000 cycles/ms, 32 MB system RAM and 640 x 480 at
60 Hz. `voodoo_maxmem=false` retains standard Voodoo 1 memory: 2 MB framebuffer
and one TMU with 2 MB texture RAM. Maps, font and profiler textures use
991,232 bytes (968 KiB) of the TMU.

OpenGL and software Voodoo both pass the small alpha/additive/depth controls.
This establishes those tested operations; it does not remove the separate
OpenGL mip-chain limitations documented by [`mipmaps`](../mipmaps/README.md).
This scene uses base-level textures.

The profiler measures guest CPU/API time. The RTC FPS counter counts
completed paced frames in guest time. `./soak.ps1` independently measures
1,440 frames with the Windows wall clock, including the profiler for the
second half, so real throughput is checked separately.

An initial run averaged near 60 FPS but missed a few refreshes during the
profiler's dashboard clear. Unrolling that C fill loop reduced its burst
cost and restored a full 60 FPS tour. The image contents and dashboard
refresh schedule are unchanged by this optimization. String-constant font
setup is also reused across characters rather than repeated per glyph.

The final measured run completed 1,440 frames at **60.01 Windows-clock FPS**,
with no guest frame above 18 ms (maximum 17.19 ms), including the profiler
for the second half of the route.

## Build and checks

Run `./setup.ps1` once or `./build.ps1` after changes. The build shares the
cathedral renderer, orbit-input helpers and profiler clock/history module;
this folder supplies its own interior model, camera, appearance and effects.
The vendored SDK/runtime and shared Open Watcom compiler are used as before.
Configs mount the parent `3dfx` folder to access the shared material files.

From this folder:

- `dosbox-x.exe -conf control.conf`: small OpenGL-backed pixel controls.
- `dosbox-x.exe -conf software.conf`: the same controls on software Voodoo.
- `dosbox-x.exe -conf test.conf`: controls, camera continuity/pause checks,
  independent effect captures, sorting comparison and a 360-frame tour.
- `./soak.ps1`: a 1,440-frame full-route test, with real throughput measured
  outside the emulator. It fails on guest frames over 18 ms or invalid poses.

The controls average a 16 x 16 RGB565 patch and allow 12 channel units for
quantization/backend differences. Expected results over black include:

| Control | Expected RGB |
| --- | --- |
| Far blue at half alpha, then near red at half alpha | 128, 0, 64 |
| Reversed alpha order | 64, 0, 128 |
| Two half-alpha additive red layers | 255, 0, 0 |
| Blue glow behind an opaque green foreground | 0, 200, 0 |
| Soft-texture alpha times half vertex alpha | 100, 50, 25 |
| Known ARGB4444 glass sample at half vertex alpha | 6, 62, 75 |

All six controls pass on both backends. Same-pose scene tests also verify
visible changes for every effect toggle and reversed sorting. Captures are
`NAVE.PPM`, `GLASS.PPM`, `NOGLASS.PPM`, `NOCANDLE.PPM`, `NOMIST.PPM`,
`NOLIGHT.PPM`, `WRONG.PPM` and `PROFILER.PPM`; results go to `BLENDING.LOG`.
Logs/captures and copied runtime files are ignored; source and executable
are included.

Relevant APIs: `grAlphaBlendFunction`, `grAlphaCombine`, `grAlphaTestFunction`,
`grDepthBufferFunction`, `grDepthMask` and `grDepthBiasLevel` in the
[Glide Reference](../Glide_Reference_Manual_2.4_199707.pdf), plus the alpha/depth
chapter of the [Programming Guide](../Glide_Programming_Guide_2.4_199707.pdf).
